# Bookshelf: посібник адміністратора

Для тих, хто розгортає й підтримує сервер. Користувацькі функції описані в [user-guide.md](user-guide.md).

## 1. Як усе влаштовано на сервері

```
Інтернет ──► Caddy (HTTPS) ──► web (nginx: SPA + проксі /api) ──► app (php-fpm, Laravel) ──► mysql
```

Усе працює в Docker Compose на одній машині: файл `docker-compose.prod.yml`, каталог `/opt/bookshelf`.
Секрети лежать лише в `/opt/bookshelf/production.env` (його створює `bootstrap-server.sh`; не копіюйте його нікуди).

Усі команди нижче виконуються на сервері в `/opt/bookshelf`. Скорочення:

```bash
cd /opt/bookshelf
dc="docker compose --env-file production.env -f docker-compose.prod.yml"
```

## 2. Розгортання

Повна покрокова інструкція (Azure for Students, ключ SSH, домен, секрети GitHub, перший деплой, типові проблеми)
в [deploy.md](deploy.md). Коротко:

1. Створити віртуальну машину (Ubuntu 24.04 x64, 1 ГБ RAM достатньо для навчального навантаження) і домен.
2. Один раз на сервері: `sudo bash bootstrap-server.sh <домен>`. Скрипт ставить Docker, створює `/opt/bookshelf`,
   `production.env` зі свіжими паролями, swap і щоденний бекап.
3. У GitHub: environment `production`, секрети `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`,
   змінні `DEPLOY_DOMAIN` і `DEPLOY_ENABLED=true`.
4. Мерж у `main` з зеленим CI публікує образи (GHCR) і викочує їх на сервер.

Перевірка, що сервер живий: `https://<домен>/up`.

### Налаштування, які варто знати

У `docker-compose.prod.yml` для контейнера `app` задано:

| Змінна | Значення | Що це означає |
|---|---|---|
| `APP_ENV` / `APP_DEBUG` | `production` / `false` | без деталей помилок у відповідях |
| `LOG_CHANNEL` / `LOG_LEVEL` | `stderr` / `warning` | журнал іде в логи контейнера |
| `SESSION_DRIVER`, `SESSION_LIFETIME` | `database`, `43200` хв | сесії в базі, живуть 30 діб |
| `CACHE_STORE`, `QUEUE_CONNECTION` | `database` | кеш і черга в MySQL |
| `MAIL_MAILER` | `log` | **листи не надсилаються, а пишуться в журнал** |

**Важливо про пошту.** Лист для відновлення пароля у цій конфігурації потрапляє в журнал `app`, а не користувачу.
Щоб листи реально йшли, треба змінити `MAIL_MAILER` і додати `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`,
`MAIL_PASSWORD`, `MAIL_FROM_ADDRESS` (змінні підтримує `backend/config/mail.php`) у секцію `app` файлу
`docker-compose.prod.yml` та в `production.env`. Поки що адміністратор може знайти посилання в логах:
`$dc logs app | grep -i reset-password`.

## 3. Резервні копії

### Створення

`/opt/bookshelf/backup.sh` робить стиснений дамп бази (`mysqldump --single-transaction`) у
`/opt/bookshelf/backups/bookshelf-ДАТА-ЧАС.sql.gz` і видаляє дампи старші за 14 днів.

- **Щоденний запуск:** `bootstrap-server.sh` ставить cron-завдання `/etc/cron.d/bookshelf-backup`: щодня о **03:00**
  від імені користувача деплою, журнал у `/opt/bookshelf/backup.log`. Повторний запуск скрипта не дублює завдання.
- **Вручну:** `bash /opt/bookshelf/backup.sh`.
- Усе, що зберігає застосунок (книги, цитати, пости, очищений текст завантажених EPUB), лежить у базі, тож дамп
  містить усе. Оригінальні EPUB-файли не зберігаються, окремого тому з файлами немає.
- Дампи лежать на тому ж диску, що й база. **Копіюйте їх за межі сервера**:
  `scp -i ~/.ssh/bookshelf_deploy azureuser@<IP>:/opt/bookshelf/backups/* .`

### Відновлення

Окремого скрипта відновлення в репозиторії немає. Стандартна процедура з дампа `mysqldump` (дамп створює таблиці
заново, тому база `bookshelf` має існувати, а вона створюється контейнером `mysql` автоматично):

```bash
cd /opt/bookshelf
dc="docker compose --env-file production.env -f docker-compose.prod.yml"

# 1. Зупиніть застосунок, щоб ніхто не писав у базу під час відновлення
$dc stop app

# 2. Завантажте дамп (замініть ім'я файлу)
gunzip -c backups/bookshelf-2026-11-23-0300.sql.gz \
  | $dc exec -T mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" bookshelf'

# 3. Запустіть застосунок і перевірте міграції
$dc start app
$dc exec -T app php artisan migrate --force
```

Перший раз перевірте процедуру на тестовому сервері або на копії, а не на бойовій базі. Відновлення замінює всі
дані станом на момент дампа.

## 4. Оновлення

**Звичайне оновлення:** мерж у `main`. CI збирає образи, а крок деплою копіює файли в `/opt/bookshelf` і запускає
`rollout.sh`, який:

1. `pull` нових образів;
2. `up -d --remove-orphans` (перезапуск стека);
3. `php artisan migrate --force` (**нові міграції накочуються автоматично**);
4. `docker image prune -f`.

**Перед оновленням з міграціями** зробіть бекап вручну (`bash /opt/bookshelf/backup.sh`).

**Відкат:** повторний запуск старого успішного прогону в Actions (Re-run), або на сервері:
`bash /opt/bookshelf/rollout.sh ghcr.io/sashacn <sha коміту>`. **Міграції автоматично не відкочуються.** Якщо нова міграція
змінила схему, для відкату відновіть базу з дампа до оновлення (розділ 3).

**Лише міграції вручну:** `$dc exec -T app php artisan migrate --force`.

## 5. Модерація

Інтерфейсу модератора немає, модерація ведеться командами Artisan. Прапорець `users.is_admin` у базі існує як
технічна роль, але команди його не перевіряють: доступ до команд означає доступ до сервера.

Запуск (на сервері; у локальній розробці замість цього `docker compose exec app php artisan ...`):

```bash
$dc exec app php artisan moderation:reports
```

### Коли що відбувається

- Читач скаржиться на пост чи коментар (причина `spam`, `abuse` або `other`).
- Коли відкритих скарг від **3 різних** читачів стає три, об'єкт **автоматично ховається**: бачить лише автор з
  позначкою «Приховано модерацією».
- Модератор дивиться скарги й вирішує: лишити прихованим, повернути або просто закрити скаргу.

### Команди

| Команда | Що робить |
|---|---|
| `moderation:reports` | таблиця відкритих скарг, найстаріші першими: id скарги, про що, причина, хто скаржиться, пояснення, стан (`visible`/`hidden`/`deleted`), початок тексту, час |
| `moderation:hide {type} {id}` | ховає пост чи коментар від усіх, крім автора, і закриває відкриті скарги на нього |
| `moderation:restore {type} {id}` | повертає прихований пост чи коментар усім і закриває відкриті скарги на нього |
| `moderation:resolve {report}` | позначає одну скаргу як розглянуту, **не змінюючи** видимості об'єкта |

`{type}` це `post` або `comment`. `{id}` це id поста чи коментаря (число). `{report}` це id скарги з `moderation:reports`.
Некоректний тип, не число або неіснуючий id дають помилку й код виходу 1.

### Приклади

```bash
# Подивитись відкриті скарги
php artisan moderation:reports

# Скарга справедлива: сховати пост 42 (скарги на нього закриваються)
php artisan moderation:hide post 42

# Сховати коментар 17
php artisan moderation:hide comment 17

# Скарги хибні, а пост було автоприховано: повернути
php artisan moderation:restore post 42

# Закрити одну скаргу (id 5), не чіпаючи самого поста
php artisan moderation:resolve 5
```

Нюанси:
- `resolve` останньої скарги на прихований об'єкт **не повертає** його: команда попередить і підкаже
  `moderation:restore`. Інакше об'єкт лишається прихованим.
- `restore` закриває скарги, щоб одна нова скарга не сховала об'єкт знову.
- Видалення автором (поста, акаунта) прибирає й скарги на нього; у таблиці вони з'являються зі станом `deleted`, якщо
  об'єкт зник.
- Відомий ризик: реєстрація відкрита, тому три нові акаунти можуть сумісно сховати чужий пост. Повертайте через
  `moderation:restore`.

## 6. Логи

Журнал застосунку йде в `stderr` контейнера, рівень `warning`:

```bash
$dc logs -f app caddy          # стежити за застосунком і Caddy
$dc logs --tail=200 app        # останні 200 рядків
$dc logs mysql                 # база
cat /opt/bookshelf/backup.log  # журнал нічного бекапу
```

Стан і ресурси: `$dc ps`, `docker stats`, `free -m`, `swapon --show`. Таблицю типових проблем (сертифікат, пам'ять,
ssh) дивіться в кінці [deploy.md](deploy.md).

## 8. Корисні ліміти, які бачить адміністратор

| Що | Значення |
|---|---|
| Завантаження EPUB | файл до 15 МБ (nginx пропускає тіло до 25 МБ лише на цьому маршруті, решта API до 2 МБ); 20 завантажень на годину на читача; одночасно сервер розбирає одну книгу, інші чекають 5 с |
| Текст читача | до 30 книг і 40 млн символів |
| Імпорт Goodreads | до 2000 книг, 2 МБ, 5 на годину |
| Експорт даних | 3 на годину |
| Вхід | 5 спроб на хвилину (email + IP) |
| Реєстрація | 30 на годину з однієї IP |
| Каталог Open Library | 30 пошуків на хвилину на читача, відповіді кешуються 24 години |
